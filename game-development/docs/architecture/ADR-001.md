# ADR-001 — Dirección evolutiva para Spec-First Guardian

**Estado:** DRAFT — decisión propuesta, no aceptada ni normativa  
**Fecha:** 2026-11-06  
**Autor:** Buffy (borrador para revisión humana)  
**Alcance:** registrar decisiones sobre dirección arquitectónica y límites de fase.  
**Autoridad documental:** sólo el usuario puede aprobar; hasta entonces prevalece el diseño vigente aprobado de SPEC-001 y no autoriza código.  
**Dependencias:** ARCH-001, CURRENT-STATE-MAP, SPEC-ARCH-001-HARDENING, PLAN-ARCH-001, FINDINGS-ARCH-001.

## Contexto

El código reúne validación documental, aprobación criptográfica, servicio de autoridad, gate, filesystem y auditoría; la Skill y algunas instrucciones afirman más cobertura que la ejecución técnica demostrada. La evolución debe modularizar responsabilidades sin rehacer el producto ni convertirlo prematuramente en plataforma.

## Decisiones propuestas

### D-1 — Evolución modular, no microservicios por defecto

Adoptar módulos lógicos con interfaces y contratos versionados. Mantener pocos procesos: Agent Runtime no confiable, Authority Service protegido, y Workspace Broker separado cuando su privilegio lo justifique. Audit & Management puede vivir como subsistema de Authority en fase inicial, con salud fail-stop durable. No crear servicios de red/servicios independientes por componente por mera simetría.

**Consecuencia:** contratos internos limpios y menor superficie operativa; fronteras de privilegio externas requieren IPC autentificado, recovery y operación comprobables.

### D-2 — Authority y ejecución no comparten responsabilidad decisoria

Authority autentica usuario, verifica SPEC/policy/scope, firma y decide. Workspace Broker sólo ejecuta orden acotada validada y no acepta llamadas directas del agente como autoridad. Si proceso único es requisito temporal, el privilegio operativo debe estar explícitamente acotado y no anunciarse como broker separado.

**Consecuencia:** reduce impacto de compromiso de proceso; requiere protocolo y coordinación transaccional.

### D-3 — Aprobación OIDC transaccional y humana

Producción sigue bloqueada hasta callback OIDC Authorization Code + PKCE, sesión server-side, validación state/nonce/issuer/audience/subject/auth_time, replay protection y confirmación humana ligada a hash de SPEC y alcance. APPROVED/Authorization activa sólo después de commit duradero del registro, bundle y evidencia de auditoría. Siete estados oficiales de SPEC no se alteran; desafío y autenticación usan máquinas de estado separadas.

**Consecuencia:** no hay compatibilidad con token directo como prueba de login. Registro legado conserva valor histórico sin elevar privilegios.

### D-4 — Separar SPEC de PLAN con compatibilidad explícita

SPEC define qué/por qué/requisitos/alcance/criterios/validación/trazabilidad; PLAN define cómo/secuencia/tareas/archivos/dependencias/rollback/evidencias. PLAN referencia una revisión/hash de SPEC y no puede alterar requisitos ni aceptación. Validador reconoce formato legado con diagnóstico y versión; migrar sólo mediante conversión explícita, guardar original/hash, no reescribir aprobaciones históricas ni invalidar documentos silenciosamente.

**Consecuencia:** cambiar validador, schema, templates, docs y fixtures exige nueva SPEC aprobada; mantener modo legacy de lectura/aprobación según política futura que apruebe el usuario.

### D-5 — Consentimiento no se infiere de paginación

Offsets/hash/count prueban el contenido que servidor entregó, no que UI lo mostró ni que una persona leyó. La autoridad debe servir vista autenticada del texto completo y del scope; el usuario confirma de forma explícita un hash exacto mediante interfaz/capacidad no invocable por el agente. No afirmar comprensión.

### D-6 — Auditoría fail-stop de proceso y persistente

Un estado de auditoría no verificable bloquea concesiones. Persistencia de health/block y el emergency latch de proceso son necesarios; `_poisoned` local a instancia no basta. Fallo simultáneo de log, marcador, health o directorio provoca denegación global en el proceso hasta reinicio con preflight/reconciliación. Si mecanismo durable tampoco puede escribirse, estado no puede ser saludable. Reconciliación humana autenticada crea evidencia; no borra historial corrupto.

Estados distintos: `HEALTHY`, `AUDIT_INCOMPLETE`, `AUDIT_CORRUPT`, `AUDIT_UNAVAILABLE`, `RECONCILIATION_REQUIRED`.

### D-7 — Workspace: allowlist de mounts, no confiar sólo en root

Inspeccionar mount ID/type/device y límites por entry; detectar mounts anidados/bind mounts, hardlinks, symlinks, archivos especiales y races. Política inicial propuesta: rechazar todo mount interno no explícitamente configurado y verificar inode/nlink y ACL por entry. Desconocido ⇒ no protegido. `protect()` debe actuar sobre snapshot/FD anclados o verificar nuevamente; no se afirma atomicidad de recorrido actual.

### D-8 — Durabilidad explícita

No ignorar fsync errors. Operación reporta separado `executed`, `data_synced`, `directory_synced`, `durability=CONFIRMED|NOT_VERIFIABLE|FAILED`, más audit receipt. Resultado ambiguo después del syscall produce `INDETERMINATE`, no durable success; gate detiene futuras operaciones y exige reconciliación.

### D-9 — Instalador declarativo e idempotente

Exponer `INSTALL`, `VERIFY`, `UPGRADE`, `RECONFIGURE`; cada modo tiene preconditions, plan/diff, backups y audit trail. No reemplazar trust store, client key pin, config personalizada o revocaciones al reinstalar. Reinstalación conserva trust/revoked state; rotación explicitamente aditiva y auditada; cambio UIDs/proyecto requiere aprobación/revalidación de workspace y socket/pins.

### D-10 — Skills universales y dominios

Evolucionar, tras migración aprobada, a `skills/spec-first-guardian/SKILL.md` y `skills/domains/{game-development,web-development,backend-development}/`. La universal contiene gobernanza independiente de dominio; las especializaciones contienen prácticas y referencias concretas. La Skill sólo afirma A (gate-mediated), B (OS-restricted), C (not protected) conforme a evidencia.

### D-11 — Extensibilidad agnóstica, plataforma no ahora

Fases: Framework Core (única prioridad), integraciones/adaptadores, plataforma de gobernanza, ecosistema/marketplace. Contratos versionados, SPI/adapters y suite de conformidad habilitan crecimiento. No construir marketplace, billing, SaaS, editor, modelos ni orquestador en fase actual.

## Alternativas consideradas

1. **Conservar monolito indiferenciado:** menos cambios iniciales, pero confunde autoridad/ejecución, limita fallos aislados y mantiene duplicaciones. Rechazada como destino; el código actual puede seguir desplegado como pocos procesos durante transición.
2. **Un microservicio por componente:** despliegue aislado pero aumenta complejidad, red, identidad interservicio, operaciones y superficie de ataque sin justificar escala. Rechazada.
3. **Plataforma SaaS inmediata:** contradice visión de framework y escala actual, añade multi-tenant/privacidad/facturación antes de core verificable. Rechazada.
4. **Implementar antes de decisión documental:** viola Etapa A/B y el principio de aprobación humana. Rechazada.

## Consecuencias, riesgos y preguntas de aprobación

- Debe aprobarse explícitamente proceso/permisos del broker, política de SPEC legacy, protocolo de callback/UI, almacenamiento durable y política de montajes/hardlinks.
- Compatibilidad Linux inicial; macOS/Windows permanecen fuera de garantía hasta adaptadores y pruebas.
- Este ADR no renombra ni mueve módulos, ni modifica estados o código.

## Estado
